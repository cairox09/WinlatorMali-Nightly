# Winlator Mali Nightly

[![Sync Winlator Mali builds](https://github.com/cairox09/WinlatorMali-Nightly/actions/workflows/sync.yml/badge.svg)](https://github.com/cairox09/WinlatorMali-Nightly/actions/workflows/sync.yml)
[![Nightly Release](https://img.shields.io/badge/release-nightly-blue)](https://github.com/cairox09/WinlatorMali-Nightly/releases/tag/nightly)
[![Upstream](https://img.shields.io/badge/upstream-WinlatorMali-blue)](https://github.com/GunaCharanTeja/WinlatorMali)

Automated unofficial mirror of APK builds generated by the GitHub Actions workflow from **[GunaCharanTeja/WinlatorMali](https://github.com/GunaCharanTeja/WinlatorMali)**.

The upstream project distributes development builds through **GitHub Actions artifacts** rather than relying exclusively on normal GitHub Releases.

This repository automatically discovers the newest available Winlator Mali build artifacts, validates them, extracts the APKs, and republishes them through a permanent rolling GitHub Release with stable download URLs.

This makes the upstream builds significantly easier to:

- download
- preserve
- verify
- share
- track
- install
- update automatically with tools such as Obtainium

> [!IMPORTANT]
> This is an **unofficial mirror**.
>
> The APKs published here come directly from the upstream GitHub Actions artifacts.
>
> This repository does **not** patch, rebuild, decompile, modify, or re-sign the APKs.

> [!NOTE]
> This repository does not develop Winlator Mali and does not create independent Winlator Mali builds.
>
> It only mirrors publicly available APK artifacts generated by the upstream project's GitHub Actions workflow.

## Build variants

Winlator Mali currently defines multiple Android product flavors.

| Variant | Android package | Description |
| --- | --- | --- |
| **Standard** | `com.winlator.mali` | Normal Winlator Mali package |
| **AnTuTu** | `com.antutu.ABenchMark` | Alternate package identity using the AnTuTu package name |
| **Ludashi** | `com.ludashi.benchmark` | Alternate package identity using the Ludashi package name |

Because these Android package names are different, Android treats the variants as separate applications.

A build from one flavor should therefore not automatically be assumed to be an in-place update for another flavor.

Use the variant corresponding to the package you already have installed.

## Automatic synchronization

The repository continuously watches the upstream GitHub Actions artifacts for new Winlator Mali builds.

The scheduled workflow checks upstream approximately every **5 minutes**.

The configured schedule is:

```text
:02
:07
:12
:17
:22
:27
:32
:37
:42
:47
:52
:57
```

GitHub Actions scheduled workflows may occasionally start later than their nominal scheduled time depending on GitHub infrastructure load.

The workflow can also be triggered manually through the repository's **Actions** tab.

Changes to the workflow itself on the `main` branch also trigger a synchronization run.

---

## Dynamic artifact discovery

The mirror is not hardcoded to only one APK flavor.

It searches for upstream build artifacts matching the Winlator Mali naming structure and tracks the newest available artifact for each build channel.

Examples include:

```text
winlator-mali-standard-release
winlator-mali-antutu-release
winlator-mali-ludashi-release

winlator-mali-standard-debug
winlator-mali-antutu-debug
winlator-mali-ludashi-debug
```

If upstream publishes another compatible build flavor following the same artifact structure, the synchronization workflow can discover it automatically.

This means the mirror does not need to be manually rewritten every time upstream chooses to generate another supported variant.

---

## Multi-APK artifacts

The synchronization workflow also supports artifacts containing more than one APK.

For example, upstream may generate an artifact structured like:

```text
artifact.zip
├── standard/
│   └── release/
│       └── app-standard-release.apk
├── antutu/
│   └── release/
│       └── app-antutu-release.apk
└── ludashi/
    └── release/
        └── app-ludashi-release.apk
```

The mirror can detect each APK separately and publish them as independent GitHub Release assets:

```text
Winlator-Mali-Standard-Release.apk
Winlator-Mali-Antutu-Release.apk
Winlator-Mali-Ludashi-Release.apk
```

This allows one rolling Release to expose every useful APK generated by the upstream workflow.

## How the mirror works

The synchronization workflow is located at:

[`.github/workflows/sync.yml`](.github/workflows/sync.yml)

For every relevant upstream artifact channel, the workflow performs the following process:

1. Queries the upstream GitHub Actions artifacts.
2. Filters out expired artifacts.
3. Filters artifacts to the configured upstream branch.
4. Detects Winlator Mali build artifact names.
5. Selects the newest artifact for each build channel.
6. Reads the upstream workflow run associated with the artifact.
7. Confirms that the upstream workflow run completed successfully.
8. Confirms that the artifact came from the expected upstream workflow.
9. Downloads the original artifact ZIP.
10. Reads the artifact digest reported by GitHub when available.
11. Calculates the downloaded ZIP SHA-256.
12. Compares both hashes.
13. Stops the workflow if integrity verification fails.
14. Searches the artifact ZIP for APK files.
15. Extracts every APK found inside.
16. Determines the APK flavor and build type.
17. Gives each APK a stable Release asset name.
18. Leaves the APK itself unchanged.
19. Generates a SHA-256 checksum for each APK.
20. Creates the rolling `nightly` Release if it does not already exist.
21. Uploads new APK assets.
22. Replaces older assets of the same build channel.
23. Updates the Release notes with upstream traceability information.

The result is effectively:

```text
GunaCharanTeja/WinlatorMali
        ↓
GitHub Actions
        ↓
Build artifact ZIP
        ↓
Artifact discovery
        ↓
Workflow validation
        ↓
SHA-256 verification
        ↓
APK extraction
        ↓
APK kept unchanged
        ↓
APK SHA-256 generation
        ↓
Rolling GitHub Release
        ↓
Stable download URL
        ↓
Obtainium / direct download
```

## Integrity verification

Integrity checking is one of the main goals of this mirror.

When GitHub exposes a digest for an upstream Actions artifact, the workflow reads that digest.

For example:

```text
Expected:
sha256:c17e21ff56f3def190355c461f9d643d9888809386c5ff0651c7f2c2d0c4afe1
```

The mirror then calculates the SHA-256 of the ZIP it actually downloaded.

Example:

```text
Actual:
sha256:c17e21ff56f3def190355c461f9d643d9888809386c5ff0651c7f2c2d0c4afe1
```

The APK is only processed if the verification succeeds.

If the hashes differ, synchronization stops instead of publishing the artifact.

---

## APK preservation

The APK itself is extracted directly from the verified upstream artifact.

The mirror does not:

- patch the APK
- rebuild the APK
- decompile and recompile the APK
- modify the Android manifest
- change the package name
- alter native libraries
- change Wine components
- change Box64 components
- modify application resources
- run `zipalign` again
- replace the APK signature
- re-sign the APK

The intention is to redistribute the exact APK file produced inside the upstream GitHub Actions artifact.

---

## APK checksums

After extracting an APK, the workflow generates an individual SHA-256 checksum.

For example:

```text
Winlator-Mali-Antutu-Release.apk
Winlator-Mali-Antutu-Release.apk.sha256
```

The `.sha256` file allows users to verify the downloaded APK independently.

## Rolling Release design

This repository deliberately uses a single rolling Release:

```text
nightly
```

Instead of creating a new GitHub Release every few minutes or every time upstream generates another development build, the existing Release is updated.

For example:

```text
Winlator-Mali-Antutu-Release.apk
```

keeps the same stable URL.

When a newer upstream AnTuTu Release artifact is detected:

```text
Old asset
    ↓
Winlator-Mali-Antutu-Release.apk
    ↓
replaced by
    ↓
New upstream APK
```

The filename and URL remain stable while the actual APK becomes the newest upstream build.

This prevents the repository from accumulating hundreds of development Releases and makes automatic update tools much easier to use.

## Obtainium

This mirror is designed to work particularly well with **[Obtainium](https://github.com/ImranR98/Obtainium)**.

The original upstream distribution format is:

```text
GitHub Actions
      ↓
Artifact ZIP
      ↓
APK inside ZIP
```

That format is inconvenient for normal automatic application updating.

This mirror converts it into:

```text
GitHub Release
      ↓
Direct APK URL
```

For Obtainium, use the permanent URL corresponding to your installed flavor.

For example, for the AnTuTu Release variant:

```text
https://github.com/cairox09/WinlatorMali-Nightly/releases/download/nightly/Winlator-Mali-Antutu-Release.apk
```

Use:

```text
Direct APK Link
```

as the Obtainium source type.

The APK remains at the same URL.

When a newer upstream build replaces the old APK, Obtainium can detect that the file changed and offer the newer build.

## GitHub Actions artifacts vs this mirror

Original GitHub Actions artifacts have several disadvantages for normal end users.

They may:

- expire
- disappear after their retention period
- require downloading a ZIP
- require manually extracting the APK
- have inconvenient artifact download URLs
- be difficult to track with automatic update applications
- not appear in the repository's normal Releases page

This mirror solves those distribution problems without changing the APK.

## Traceability

The rolling Release records information about the upstream artifacts synchronized during each update.

Information may include:

```text
Artifact name
Artifact ID
Workflow run ID
Upstream commit SHA
Artifact creation timestamp
```

Example:

```text
winlator-mali-antutu-release

Artifact:
9939630506

Run:
33880294793

Commit:
a5c409dfec7a

Created:
2026-09-04T13:52:57Z
```

This makes it possible to trace a mirrored APK back to the upstream GitHub Actions workflow run that produced it.

## Update behavior

The mirror tracks build channels independently.

Imagine upstream currently provides:

```text
winlator-mali-standard-debug
winlator-mali-antutu-release
```

The Release may contain:

```text
Winlator-Mali-Standard-Debug.apk
Winlator-Mali-Antutu-Release.apk
```

Later upstream may generate:

```text
winlator-mali-standard-release
```

The mirror can then add:

```text
Winlator-Mali-Standard-Release.apk
```

without removing unrelated build channels.

If another new AnTuTu Release build appears later, only:

```text
Winlator-Mali-Antutu-Release.apk
```

needs to be replaced.

---

## Why synchronization checks frequently

Upstream builds are development artifacts and may be published without a formal GitHub Release.

The mirror therefore checks the upstream Actions artifacts frequently so that a newly published build becomes available through the rolling Release shortly afterward.

The goal is:

```text
Upstream build published
        ↓
Mirror detects it
        ↓
Artifact verified
        ↓
APK extracted
        ↓
Nightly Release updated
        ↓
Obtainium can detect the new APK
```

No manual download, extraction, or Release creation should be required.

---

## Failure behavior

The workflow is intentionally designed to fail instead of silently publishing questionable data.

Examples of conditions that can stop synchronization include:

- no matching upstream artifacts
- unsuccessful upstream workflow run
- unexpected upstream workflow
- unexpected upstream branch
- artifact download failure
- artifact SHA-256 mismatch
- artifact containing no APK
- empty extracted APK
- GitHub Release upload failure

A failure appears in the repository's **Actions** tab.

This is preferable to publishing an invalid or unverifiable APK.

## Security model

This mirror reduces some distribution risks but should not be interpreted as an independent security audit of Winlator Mali.

The mirror verifies that the downloaded Actions artifact matches GitHub's reported artifact digest when that digest is available.

It then republishes the APK extracted from that artifact without intentional modification.

This verifies the mirroring path:

```text
GitHub Actions artifact
        ↓
Downloaded artifact
        ↓
Mirror Release
```

It does **not** independently audit the application source code or guarantee that upstream software itself is safe.

Users should still make their own trust decisions regarding the upstream project.
